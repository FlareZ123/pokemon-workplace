# Post-Knock-Out Prize and game resolution

## Question

After a simultaneous Knock Out batch is known, how should Prize taking and terminal game resolution compose with the existing physical-state kernels?

Implementation: `tools/post_knockout_game_resolution.py`  
Regression: `results/post_knockout_game_resolution/reproduce.py`

## Rule-derived phase boundary

The Advanced Player's Rulebook orders Knock Out resolution as:

1. apply effects triggered by the Knock Out;
2. discard the Knocked Out Pokémon and attached cards;
3. both players take any Prize cards earned from those Knock Outs;
4. if both Active Pokémon were Knocked Out, the player whose turn would be next promotes first.

The Win and Loss section says a player loses when the opponent has taken all Prize cards, when that player has no Pokémon in play, or when that player cannot draw at the beginning of their turn. It then gives an explicit 11-row table for cases where Prize completion and no-Pokémon conditions occur simultaneously.

This means a state engine needs a terminal check after the complete Knock Out set and Prize awards are known. Requiring a replacement Active before evaluating that terminal snapshot can add a decision to a game that has already ended.

## A compact form of the 11-row table

For each player `P`, define a loss-condition count over the two conditions that can arise together around Knock Out resolution:

- `1` if the opponent has taken all Prize cards;
- `1` if `P` has no Pokémon remaining in play.

The rulebook table is exactly reproduced by comparing those counts:

- both counts zero: game continues;
- equal positive counts: tie;
- otherwise, the player with more fulfilled loss conditions loses.

The regression evaluates all 11 simultaneous-condition rows from the rulebook table plus the four ordinary one-sided Prize/no-Pokémon cases.

This is a derived representation of the table, not a replacement rule. Its value is that the simulator can preserve one small invariant instead of encoding eleven unrelated branches.

## Integration with the Knock Out phase

`resolve_post_knockout()` consumes the existing `TwoPlayerKnockOutPhase` and computes each player's surviving Pokémon directly from the complete pending Knock Out set.

Prize awards are then applied to each player's remaining Prize count. The resolver records:

- Prize cards remaining before the batch;
- the award generated by the Knock Outs;
- the number actually taken;
- Prize cards remaining afterward;
- surviving Pokémon count.

The terminal table is evaluated from that post-award snapshot before any replacement-Active policy is needed.

## Regression examples

### Final Prize and last Pokémon at the same time

Player A has one Prize card remaining, earns a two-Prize award, and loses their only Pokémon in the same batch. Player B still has a Pokémon.

After the batch:

- A has taken their final Prize;
- A has no Pokémon;
- B has not taken all Prizes;
- B still has a Pokémon.

A fulfills one loss condition through having no Pokémon. B fulfills one loss condition because A took all Prizes. The resolver returns a tie, matching the corresponding rulebook row.

### Both players take the final Prize, one also has no Pokémon

Both players reach zero remaining Prize cards. Player B also has no Pokémon while Player A has a survivor.

Player A therefore fulfills one loss condition. Player B fulfills two. The resolver returns a Player A win, again matching the rulebook table.

## Other terminal rules

The same module also represents the two remaining Win and Loss rules outside the Knock Out table:

- beginning-of-turn deck-out: the player beginning the turn loses if they cannot draw;
- tiebreaker progress: after a tied game when a winner is required, the first player with fewer Prize cards remaining wins.

These are kept as separate functions because their timing differs from the post-Knock-Out simultaneous-condition check.

## Findings

Terminal game resolution is another phase boundary rather than a Boolean attached to one transition.

In particular, a planner should preserve the complete set of simultaneous loss conditions produced by one Knock Out event. Resolving the first observed condition immediately can produce the wrong result when the same event also completes a Prize race or removes the opponent's final Pokémon.

The 11-row rulebook table admits a simple loss-condition-count representation, and the regression verifies that equivalence exhaustively for every listed row.

## Limits

This result tracks Prize counts, not the physical identity of Prize cards moved to hand. The existing Prize belief layer also does not yet implement Prize-taking transitions. A future integration should update physical hidden-zone truth and the player's belief state together.

The `prize_award` value is supplied by upstream card semantics. This module does not decide whether a Knocked Out Pokémon awards one, two, three, fewer, or modified Prize cards.

The deck-out helper assumes other terminal conditions were resolved when they arose. It does not construct impossible delayed states where an earlier Prize/no-Pokémon loss is carried into a later beginning-of-turn draw check.

The tiebreaker helper models only the rulebook's fewer-remaining-Prizes progress condition, not tournament procedure around initiating or reporting a tiebreaker.
